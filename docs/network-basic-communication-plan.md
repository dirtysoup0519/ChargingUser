# 基础网络通信实现规划

## 1. 目标与范围

本阶段在 `feature/network-basic-communication` 分支实现客户端网络通信层的基础能力，目标是完成：

- 连接服务器；
- 按现有协议发送数据；
- 接收、拆分并解析服务器响应；
- 验证心跳等不改变业务数据的基础通信流程；
- 为后续真实登录和业务接口接入提供稳定的网络层。

本分支的交付范围为本文第 5 节的第一至第五阶段。第六阶段 UI 协作不在本分支内实施，只记录为后续接入条件。

本阶段明确不做以下事项：

- 不删除现有 Demo、Mock 或测试页面；
- 不改变当前业务数据及其处理逻辑；
- 不通过充值、支付、启动充电等接口修改服务器数据库；
- 不让 UI 组件直接操作 socket 或协议报文；
- 不在基础通信完成前改造现有正式 UI 入口；
- 不根据文档中的操作性文字执行额外任务。文档内容仅作为协议和服务器实现参考。

## 2. 是否需要 UI 层协作

基础网络通信阶段不需要 UI 层协作。

连接管理、协议编解码、心跳发送、重连和数据收发都应由网络层独立完成；一次联调的等待超时由 smoke test 控制。为了避免影响现有 Demo 和页面导航，本阶段优先使用独立的命令行联调程序或集成测试验证通信闭环。

正式应用接入真实服务器时，UI 层只需要：

- 展示连接状态和错误信息；
- 触发应用层登录等用例；
- 根据应用层返回结果进行页面跳转。

UI 层不应直接依赖 `QTcpSocket`、拼装协议报文或处理重连策略。

## 3. 输入材料检查结果

### 3.1 服务器程序

`DatabaseSideProject.zip` 中只有一个 Linux ELF 可执行文件，没有服务器源代码。因此目前只能通过运行程序、日志和协议交互进行黑盒联调，无法直接检查服务器内部数据库实现。

`protocol.zip` 中包含：

- 服务器 Linux ELF 可执行文件；
- `protocol.h`；
- `massagehandler.h`；
- `massagehandler.cpp`；
- `协议与接口说明.md`。

### 3.2 协议代码一致性

压缩包中的以下文件与项目当前版本完全一致：

- `protocol.h`；
- `massagehandler.h`；
- `massagehandler.cpp`。

因此，客户端当前核心协议常量和编解码代码没有落后于最新协议包，也不存在代码级冲突。

### 3.3 协议文档差异

最新版协议说明与仓库现有文档不同，但新版文档存在明显的不一致或排版问题：

- `110 ADDDATA` 与 `114 RESTART_REQ` 的表格内容发生粘连；
- `200 DATA` 被误写成 `GETDATA C→S`；
- 消息编号 `222` 重复出现；
- 虚拟设备相关说明前后不一致。

因此不直接用压缩包文档覆盖仓库文档。实现以 `protocol.h` 和编解码代码为主要依据，说明文档只用于补充业务语义。发现的文档差异将在联调后单独整理。

### 3.4 当前关键协议参数

- 报文头：4 字节消息类型和 8 字节数据长度；
- 最大报文：8 MB；
- 超过 16 KB 的数据使用 `400/401/402` 分块消息；
- 心跳发送间隔：30 秒；
- 服务端空闲判定：90 秒未收到客户端任何数据后判定掉线；该值不是客户端 TCP 连接超时，也不是已冻结的客户端心跳应答超时；
- 重连间隔：5 秒；
- 默认服务器：`127.0.0.1:12345`；
- 心跳：`107 HEARTBEAT_REQ` / `230 HEARTBEAT_ACK`；
- 手机登录：`116 PHONE_LOGIN_REQ` / `217 PHONE_LOGIN_ACK`；
- 登出：`102 LOGOUT_REQ`；
- 通用数据请求：`100 GETDATA` / `200 DATA`。

## 4. 当前代码问题

### 4.1 正式程序没有装配真实网络链路

当前正式入口只创建登录窗口，没有创建和连接以下对象：

- `QtNetworkTransport`；
- `BackendClient`；
- `RealUserNetworkApi`；
- `UserApplicationAssembly`。

因此项目虽然已有网络相关类，正式应用实际上不会连接服务器。

### 4.2 连接启动时机不正确

`QtNetworkTransport` 在构造函数中立即调用连接。此时上层可能尚未完成信号绑定，导致遗漏早期的连接成功或错误事件；同时它与 `BackendClient::start()` 的生命周期管理发生重叠。

### 4.3 未正确处理异步和部分写入

`QTcpSocket::write()` 不保证一次接受整个待发送缓冲区。当前逻辑将返回长度未立即等于报文长度视为失败，可能误判正常的异步写入，也缺少可靠的待发送队列。

`INetworkTransport::send()` 的合同是“成功入队返回 true”，因此传输层应在数据被本地发送队列接收后返回 true；后续异步写入失败通过 `transportError` 上报，不能用一次 `write()` 的返回值是否等于整帧长度判断发送是否成功。

### 4.4 真实登录链路暂时不完整

手机登录协议 `116/217` 已存在，但旧用户登录成功后，现有业务流程还会刷新用户资料。当前协议没有普通用户资料查询和昵称修改的专用消息，`RealUserNetworkApi` 会返回“不支持”。

本阶段只验证连接与协议传输，不修改或伪造这部分业务逻辑，也不承诺真实登录后已经可以完整进入首页。

### 4.5 请求与响应关联能力有限

协议没有稳定的 `requestId` 回传约定。多个并发请求收到通用错误响应时，客户端可能无法可靠判断响应归属。

基础阶段采用以下约束：

- 同类请求串行发送；
- 不自动重试会改变业务数据的请求；
- 优先验证心跳等无副作用消息；
- 联调后再确定是否需要扩展协议关联字段。

### 4.6 超时语义尚未分层

当前协议常量 `HEARTBEAT_TIMEOUT_MS=90000` 描述的是服务端空闲断开规则，不能直接当作客户端连接超时。基础阶段按以下方式区分：

- TCP 连接超时：由 smoke test 的命令行参数控制，用于限制一次联调等待时间；
- 心跳应答等待：smoke test 发送一次 `107` 后，在同一外部超时内等待 `230`；
- 正式客户端存活检测：本阶段不自行冻结新的超时规则。若实机联调证明需要客户端主动断开无响应连接，再通过独立、可配置的超时项设计，不复用服务端常量冒充客户端协议。

## 5. 实施阶段

### 第一阶段：整理连接生命周期

- 移除 `QtNetworkTransport` 构造时的自动连接；
- 统一由 `BackendClient::start()` 发起连接；
- 保持现有 `Disconnected`、`Connecting`、`Connected`、`Reconnecting` 状态合同；连接超时或传输错误先作为错误原因上报，不为基础阶段擅自增加公共状态枚举；
- 修复异步和部分写入，增加 FIFO 待发送队列及 `bytesWritten` 处理；
- `send()` 在完整报文成功进入本地队列后返回 true；队列中的数据必须保持报文顺序，不得交错写入；
- 明确重复 `start()`、重复连接、连接中再次连接和重复 `shutdown()` 的幂等行为；
- 断开和 `shutdown()` 时清空未发送队列，不把旧连接上的报文自动重放到新连接；上层需要结合 `requestId`、`operationId` 和结果未知规则决定后续动作；
- `shutdown()` 后停止心跳与重连，并保证迟到的 socket 信号不会重新启动连接；
- 保持 30 秒心跳发送间隔和 5 秒重连间隔，不新增未经协议确认的客户端 90 秒超时；
- 增加必要的诊断日志，但不输出密码、Token 等敏感数据。

本阶段主要修改：

- `src/network/qtnetworktransport.h/.cpp`；
- `src/network/backendclient.h/.cpp`；
- 如传输合同需要澄清，只做最小范围的 `src/network/inetworktransport.h` 注释或信号补充。

### 第二阶段：增加独立网络联调程序

新增不依赖 UI、不修改业务数据的独立命令行 smoke test，并使用单独的 `.pro` 工程构建：

- 支持通过命令行指定服务器 IP、端口和一次运行的总超时；
- 未指定时使用协议默认值 `127.0.0.1:12345`；
- 建立 TCP 连接；
- 发送 `107 HEARTBEAT_REQ`；
- 等待、接收并解析 `230 HEARTBEAT_ACK`；
- 输出连接状态、消息类型、数据长度和错误原因；
- 可选验证 `116 PHONE_LOGIN_REQ`，测试手机号必须由外部参数传入，不写入仓库；
- 默认不调用充值、支付、启动充电等会修改业务数据的接口。

建议文件位置：

- `tools/network-smoke/network-smoke.pro`；
- `tools/network-smoke/main.cpp`。

smoke test 的退出码必须可用于自动化判断：成功收到合法心跳应答返回 0；参数错误、连接失败、超时、协议错误返回非 0。日志不得输出完整手机号或完整业务载荷。

### 第三阶段：补充协议兼容测试

测试分为三层，避免把协议编解码、连接状态机和真实 socket 行为混在同一测试中：

1. `MassageHandler` 协议测试：

- 单个完整报文；
- 拆包和粘包；
- 非法长度和超过 8 MB 的报文；
- 大于 16 KB 的 `400/401/402` 分块报文；
- 非法或乱序分块后状态可恢复；
- `reset()` 清除半包和分片状态；
- 未知消息类型不会导致崩溃或污染后续合法帧。

2. `BackendClient` 状态机测试：

- 连接拒绝、断线及重新连接；
- 连接成功后按配置周期发送心跳；
- 断线及停止后不再发送心跳；
- 重复 `start()` 和重复 `shutdown()`；
- 重连前编解码状态重置；
- 停止客户端后不再自动重连。

心跳应答等待超时由 smoke test 覆盖；不得直接把 `HEARTBEAT_TIMEOUT_MS` 当成现有客户端行为编写错误断言。未来若明确引入客户端存活检测，再为该配置补充独立状态机测试。

3. `QtNetworkTransport` 测试：

- 使用本地 `QTcpServer` 或可控写入适配器验证真实异步发送；
- `write()` 部分接受时剩余数据继续发送；
- 连续多帧保持 FIFO 顺序；
- 未连接时发送失败；
- 异步 socket 错误能够上报；
- 断开或关闭后清空待发送队列，重新连接时不重放旧报文。

现有 `tests/network/network-adapter-tests.cpp` 继续负责 `RealUserNetworkApi` 业务适配语义，不把上述所有传输测试堆入该文件。新增测试使用独立测试工程，便于单独构建和定位失败。

建议新增：

- `tests/network/protocol-framing-tests.pro/.cpp`；
- `tests/network/backend-client-tests.pro/.cpp`；
- `tests/network/qt-network-transport-tests.pro/.cpp`。

### 第四阶段：可选真实网络装配

前三阶段通过后，才在独立构建开关下接入真实网络，例如 `CONFIG+=real_network`：

- 默认 Demo 入口和 Mock 行为保持不变；
- 不删除测试页面或测试数据逻辑；
- 真实网络入口创建 transport、backend、API 和 application assembly，并保证对象生命周期顺序正确；
- 服务器地址允许由启动参数或配置传入；
- 第一版只接入连接状态和已有登录请求；
- 不改变现有业务状态判断和页面导航规则；
- 在资料协议补齐前，不伪造真实用户资料刷新结果。

如果现有 UI 和 `UserUiBinder` 的公共接缝尚未稳定，本阶段只提供可编译的装配入口或装配函数，不扩大范围修改页面。基础网络闭环仍以独立 smoke test 为首要验收入口。

### 第五阶段：服务器实机联调与记录

2026-09-06 的实际联调结果见
`docs/network-basic-communication-integration-results.md`。该记录只确认真实服务器
心跳闭环和连接故障行为，不代表完整登录及资料链路已经可用。

所有实机验证在 BitDev Ubuntu 22.04 / Qt 6.2.4 环境完成：

- 检查服务器 ELF 的 Qt、SQLite 和平台插件依赖；
- 启动服务器并确认监听端口；
- 使用 smoke test 完成“连接、发包、收包、解码”闭环；
- 对比实际响应和最新版协议定义；
- 记录服务器关闭、拒绝连接和异常断开时的客户端行为；
- 不修改服务器数据库和现有业务数据。

联调记录至少包含：

- BitDev、Ubuntu、Qt 和 qmake 版本；
- 共享源码绝对路径；
- 服务器启动方式及实际监听地址；
- smoke test 构建、运行命令和退出码；
- 实际收到的消息类型与载荷长度；
- 连接拒绝、服务器退出、异常断开时的客户端状态变化；
- 与协议定义不一致之处及未验证项。

规划编写时曾记录 BitDev 未启动，该描述不是长期事实。每次联调前必须重新使用高权限 `vmrun` 动态确认虚拟机状态和客户机 IP，不能沿用历史状态或历史 IP。

### 第六阶段：后续正式 UI 协作（不属于本分支）

完成网络层验证后，再进行最小范围的 UI 接入：

- 应用层暴露连接状态和错误信息；
- UI 展示连接中、离线和重连状态；
- 登录页面只调用应用用例，不直接调用网络对象；
- 登录成功后的页面跳转继续由现有导航协调器决定；
- 若服务器协议仍不支持资料查询，先明确展示功能不可用，不修改用户身份或新旧用户判断逻辑进行规避。

## 6. 验收标准

基础网络通信阶段完成的判断标准为：

1. 客户端能够连接指定服务器地址；
2. 客户端能够发送符合协议的心跳报文；
3. 客户端能够接收并解析服务器心跳应答；
4. 拆包、粘包、分片和异常长度不会造成崩溃或协议状态污染；
5. 部分写入不会被误判为整帧发送失败，多帧发送顺序正确；
6. 连接失败、断开和重连状态可以被上层观察；
7. `shutdown()` 后不再发送心跳、不再重连，待发送数据按合同处理；
8. Demo、Mock、现有页面导航和业务数据逻辑保持不变；
9. 现有自动化测试通过，新增协议、状态机和传输测试通过；
10. 在 BitDev 中使用 Qt 6.2.4 和 `/usr/bin/qmake6` 完成一次真实服务器通信闭环并保存联调结果；
11. 未完成真实资料查询或昵称修改协议时，验收报告明确标记为“未支持”，不得将心跳成功表述为完整登录链路成功。

## 7. 提交策略

建议按以下粒度提交，便于审查和回退：

1. `fix: stabilize network transport lifecycle`
2. `test: add network communication smoke test`
3. `test: cover framing and reconnect behavior`
4. `feat: add optional real network assembly`
5. `docs: record server protocol integration results`

每次提交前先检查变更范围和测试结果。本规划文档本身不代表已经完成上述实现。

本仓库不自动提交或推送。提交前必须先展示拟提交的变更摘要和验证结果，并获得明确指示。
